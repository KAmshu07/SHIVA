The Communication Problem

Let's start with a familiar story. You're building a game in Unity, and at first, everything seems simple. Your Player script needs to tell your GameManager that the player has collected a coin. Easy enough—just add a reference:

public class Player : MonoBehaviour
{
    public GameManager gameManager;
    
    private void OnTriggerEnter(Collider other)
    {
        if (other.CompareTag("Coin"))
        {
            gameManager.AddCoin();
        }
    }
}

But as your game grows, the connections multiply:

  • Your UI needs to update when coins are collected
  • Sound effects need to play
  • Achievements need to be tracked
  • The save system needs to record the change
  • Maybe an online leaderboard needs updating

Suddenly, your neat little Player script has references to dozen of other systems:

public class Player : MonoBehaviour
{
    public GameManager gameManager;
    public UIManager uiManager;
    public AudioManager audioManager;
    public AchievementManager achievementManager;
    public SaveSystem saveSystem;
    public LeaderboardManager leaderboardManager;
    // And the list keeps growing...
    
    private void OnTriggerEnter(Collider other)
    {
        if (other.CompareTag("Coin"))
        {
            gameManager.AddCoin();
            uiManager.UpdateCoinDisplay();
            audioManager.PlayCoinSound();
            achievementManager.CheckCoinAchievements();
            saveSystem.SaveGameState();
            leaderboardManager.UpdateScore();
        }
    }
}

This approach creates several problems:

1

Tight Coupling

Your Player class now knows about and depends on many other systems. Change one system, and you might need to update Player too.

2

Initialization Order Dependency

All these systems must be initialized before Player can use them.

3

Testing Difficulty

Testing Player in isolation becomes nearly impossible because it requires all these other systems.

4

Maintenance Nightmare

As your game grows, keeping track of all these connections becomes increasingly difficult.

You might try some alternative approaches:

Using Events and Delegates

public class Player : MonoBehaviour
{
    // Define an event
    public static event Action OnCoinCollected;
    
    private void OnTriggerEnter(Collider other)
    {
        if (other.CompareTag("Coin"))
        {
            // Trigger the event
            OnCoinCollected?.Invoke();
        }
    }
}

// Then elsewhere:
void Start()
{
    Player.OnCoinCollected += HandleCoinCollected;
}

void HandleCoinCollected()
{
    // React to coin collection
}

Issues with this approach:

  • Static events can cause memory leaks if not unsubscribed properly
  • No control over execution order
  • Difficult to debug when many systems are connected
  • No built-in error handling

Using Unity's SendMessage

private void OnTriggerEnter(Collider other)
{
    if (other.CompareTag("Coin"))
    {
        GameObject.Find("GameManager").SendMessage("AddCoin");
    }
}

Even worse problems:

  • Performance is poor
  • No type safety
  • No compile-time checking
  • Still creates coupling, just in a different way

Enter the Message Bus

This is where a message bus system comes to the rescue. A message bus acts as a central hub where messages are published and received, without the sender needing to know who (if anyone) is listening.

Here's how the same coin collection would work with a message bus:

public class Player : MonoBehaviour
{
    private void OnTriggerEnter(Collider other)
    {
        if (other.CompareTag("Coin"))
        {
            // Just publish a message - no need to know who's listening
            BusManager.MessageBus.Publish(new CoinCollectedMessage());
        }
    }
}

// In GameManager:
void OnEnable()
{
    BusManager.MessageBus.Subscribe(OnCoinCollected);
}

void OnDisable()
{
    BusManager.MessageBus.Unsubscribe(OnCoinCollected);
}

void OnCoinCollected(CoinCollectedMessage message)
{
    // Handle coin collection
    AddCoin();
}

// Similarly in UIManager, AudioManager, etc.

This provides several advantages:

Decoupling

The Player doesn't need to know who's interested in coin collection events

Flexibility

New systems can start listening for coin collections without modifying Player

Testability

Each component can be tested in isolation

Maintainability

The code is cleaner and easier to understand

This is where our Scoped Hierarchical Infrastructure for Versatile Architecture (SHIVA) comes in - a powerful, flexible message bus system designed specifically for Unity applications.

Your First Steps with SHBI

Let's start with the simplest possible example. First, we need to define a message:

// A simple message with no additional data
public class GameStartedMessage : BaseMessage
{
    // BaseMessage provides basic functionality like message ID
    public GameStartedMessage() : base() { }
}

// A message with data
public class PlayerMovedMessage : BaseMessage
{
    // Include any data that subscribers might need
    public Vector3 NewPosition { get; }
    public float Speed { get; }
    
    public PlayerMovedMessage(Vector3 newPosition, float speed) : base()
    {
        NewPosition = newPosition;
        Speed = speed;
    }
}

Next, let's publish a message when the game starts:

public class GameManager : MonoBehaviour
{
    private void Start()
    {
        // Tell everyone the game has started
        BusManager.MessageBus.Publish(new GameStartedMessage());
    }
}

And finally, let's have another component listen for that message:

public class PlayerController : MonoBehaviour
{
    private void OnEnable()
    {
        // Start listening for game start messages
        BusManager.MessageBus.Subscribe(OnGameStarted);
    }
    
    private void OnDisable()
    {
        // IMPORTANT: Always unsubscribe when disabled
        BusManager.MessageBus.Unsubscribe(OnGameStarted);
    }
    
    private void OnGameStarted(GameStartedMessage message)
    {
        // React to game starting
        Debug.Log("Game started! Player is ready to go.");
        // Initialize player, etc.
    }
}

Success!

That's it! You've just implemented your first message bus communication. The GameManager doesn't need to know about the PlayerController, and the PlayerController doesn't need a reference to the GameManager. They communicate through messages.

Messages and Events: The Building Blocks

In the SHIVA system, we distinguish between two types of communications:

Messages

Used for standard communications, can potentially have responses

Events

Used for one-way notifications, never have responses

This distinction helps keep your communication patterns clear and organized.

Message Types

The SHBI system provides several base message types:

  1. BaseMessage: The simplest message type with basic functionality
  2. ScopedMessage: A message that contains scope and propagation information (more on this later)

Let's define examples of each:

// Simple base message
public class PlayerJumpedMessage : BaseMessage
{
    public float JumpHeight { get; }
    
    public PlayerJumpedMessage(float jumpHeight) : base()
    {
        JumpHeight = jumpHeight;
    }
}

// We'll learn about scoped messages soon!

Event Types

Similarly, there are base event types:

  1. BaseEvent: Simple event with a timestamp
  2. ScopedEvent: Event with scope and propagation information

Here's how to define events:

// Simple base event
public class GameTickEvent : BaseEvent
{
    public int TickNumber { get; }
    
    public GameTickEvent(int tickNumber) : base()
    {
        TickNumber = tickNumber;
    }
}

When to Use Messages vs Events

Use messages when:

  • You might need a response
  • You're sending specific commands or requests
  • You want to communicate specific game actions

Use events when:

  • You're simply notifying others something happened
  • No response is expected
  • The communication is purely informational

Examples:

  • "Player jumped" is a good event - it's just information
  • "Open inventory" is a good message - it's a command that might require a response

Using the Event Bus

The SHBI system provides separate buses for messages and events:

// Publishing an event
BusManager.EventBus.Publish(new GameTickEvent(currentTick));

// Subscribing to an event
BusManager.EventBus.Subscribe(OnGameTick);

// Don't forget to unsubscribe
BusManager.EventBus.Unsubscribe(OnGameTick);

This separation keeps your message and event handling clean and organized.

Growing Pains: When a Simple Bus Isn't Enough

As your project grows, you'll start to encounter new challenges with a simple message bus approach:

Problem 1: Message Overload

With dozens or hundreds of different message types flowing through a single bus, it becomes difficult to:

  • Track which systems are publishing which messages
  • Ensure messages are only received by relevant systems
  • Debug issues when messages aren't being received as expected

Problem 2: Performance Concerns

When every message is sent to every subscriber, regardless of relevance, you may encounter performance issues:

  • UI-specific messages reaching gameplay systems that don't need them
  • Network messages being processed by local-only components
  • High-frequency messages (like physics updates) being sent to systems that only need occasional updates

Problem 3: Access Control

In a team environment, you may want to restrict which parts of your codebase can:

  • Publish specific types of messages
  • Listen to certain critical messages
  • Respond to sensitive communications

Problem 4: Message Flow Control

As your application's architecture gets more complex, you might want messages to:

  • Stay within specific subsystems
  • Propagate up to parent systems but not down to child systems
  • Flow down to subsystems but not up to parent systems

These growing pains point to the need for a more sophisticated approach. This is where the "Scoped" and "Hierarchical" parts of SHBI come into play.

Introducing Scopes: Bringing Order to Chaos

A scope in SHBI represents a logical domain or area of your application. Think of it as a dedicated communication channel for a specific part of your application.

Predefined Scopes
Global
Application-wide communication
Core
Core game systems
UI
User interface components
Networking
Network-related communications

Let's see how to use scoped communication:

// Get the UI bus specifically
var uiBus = BusManager.GetMessageBus(BusScope.UI);

// Subscribe to UI-specific messages
uiBus.Subscribe(OnWindowOpened);

// Publish to the UI bus
uiBus.Publish(new WindowOpenedMessage("MainMenu"));

By using scoped communication, you:

  • Reduce noise by keeping messages in relevant domains
  • Improve performance by only processing messages in the appropriate scope
  • Make debugging easier by clearly seeing which scope a message belongs to

Creating Custom Scopes

You can also create your own custom scopes for specific parts of your application:

// Create a custom gameplay scope as a child of the Core scope
var gameplayScope = BusManager.CreateScope("Gameplay", BusScope.Core);

// Get the bus for this scope
var gameplayBus = BusManager.GetMessageBus(gameplayScope);

// Use it like any other bus
gameplayBus.Subscribe(OnEnemySpawned);
gameplayBus.Publish(new EnemySpawnedMessage(enemyType, position));

Custom scopes let you organize your communication in a way that matches your application's architecture.

The Scope Hierarchy: Creating Structure

Scopes in SHBI aren't just separate channels - they're organized in a hierarchical structure. Each scope (except the Global scope) has a parent scope:

Global
Core
Gameplay
AI
UI
Networking

This hierarchy provides a logical organization that often mirrors your application's architecture. But it also enables an important feature: message propagation.

Creating Parent-Child Relationships

When creating scopes, you specify the parent:

// Create the hierarchy
var aiScope = BusManager.CreateScope("AI", BusScope.Core);
var enemyAiScope = BusManager.CreateScope("EnemyAI", aiScope);
var bossAiScope = BusManager.CreateScope("BossAI", aiScope);

Accessing Buses Correctly

To get the appropriate bus for a scope:

// Get the bus for the AI scope
var aiBus = BusManager.GetMessageBus(aiScope);

// Get the event bus for the UI scope
var uiEventBus = BusManager.GetEventBus(BusScope.UI);

Understanding Bus Relationships

The parent-child relationships between scopes extend to their buses. When you create a bus for a child scope, it has a reference to its parent scope's bus:

// This creates a parent-child relationship between buses
var parentBus = BusManager.GetMessageBus(parentScope);
var childBus = BusManager.GetMessageBus(childScope);

This parent-child relationship is crucial for message propagation, which we'll discuss next.

Propagation: Messages that Travel

By default, messages stay within their scope - when you publish a message to the UI bus, only subscribers to the UI bus receive it. But what if you want messages to travel up or down the scope hierarchy?

This is where scoped messages and propagation behavior come in:

// Define a scoped message with propagation behavior
public class PlayerDiedMessage : ScopedMessage
{
    public string PlayerName { get; }
    
    public PlayerDiedMessage(string playerName, BusScope scope, 
                            PropagationBehavior propagation = PropagationBehavior.Local)
        : base(scope, propagation)
    {
        PlayerName = playerName;
    }
}

// Publishing with upward propagation
var gameplayBus = BusManager.GetMessageBus(gameplayScope);
gameplayBus.Publish(new PlayerDiedMessage("Player1", gameplayScope, PropagationBehavior.UpToParent));

UpToParent
The message propagates up to the parent scope
DownToChildren
The message propagates down to child scopes
UpAndDown
The message propagates both up and down

Propagation Scenarios

Let's look at some examples of when to use different propagation behaviors:

Local Propagation

// UI-specific message that doesn't need to go elsewhere
uiBus.Publish(new ButtonClickedMessage("StartButton", BusScope.UI, PropagationBehavior.Local));

Use local propagation for messages that are only relevant within their specific domain.

Upward Propagation

// Gameplay event that Core systems might need to know about
gameplayBus.Publish(new LevelCompletedMessage(levelId, gameplayScope, PropagationBehavior.UpToParent));

Use upward propagation when child systems need to inform parent systems about important events.

Downward Propagation

// Core system broadcasting to all gameplay subsystems
coreBus.Publish(new GamePausedMessage(isPaused, BusScope.Core, PropagationBehavior.DownToChildren));

Use downward propagation when parent systems need to broadcast information to all child systems.

Up and Down Propagation

// Critical message that needs to reach the entire hierarchy
coreBus.Publish(new GameOverMessage(score, BusScope.Core, PropagationBehavior.UpAndDown));

Use up and down propagation sparingly, for truly critical messages that need to reach every part of your application.

Critical Rule for Propagation

There's one absolutely essential rule to understand about propagation:

Messages only propagate if the message's scope exactly matches the bus's scope

This means:

// This will propagate correctly because the scope matches the bus
gameplayBus.Publish(new PlayerDiedMessage("Player1", gameplayScope, PropagationBehavior.UpToParent));

// This will NOT propagate because the scope doesn't match the bus
gameplayBus.Publish(new PlayerDiedMessage("Player1", BusScope.UI, PropagationBehavior.UpToParent));

This rule is crucial for preventing unintended propagation and keeping your message flow controlled.

Access Control: Setting Boundaries

As your project grows and team size increases, you might want to control which parts of your code can access specific buses. SHBI provides a built-in access control system:

// Register access rights for an assembly
BusManager.RegisterAccess(Assembly.GetExecutingAssembly(), BusScope.UI, BusAccessLevel.ReadWrite);

Access Levels

None
No access to the bus
ReadOnly
Can subscribe but not publish
WriteOnly
Can publish but not subscribe
ReadWrite
Full access to the bus

Practical Examples

Here's how you might configure access rights in a real application:

// UI assembly gets full access to UI scope, but only read access to Core
BusManager.RegisterAccess(typeof(UIManager).Assembly, BusScope.UI, BusAccessLevel.ReadWrite);
BusManager.RegisterAccess(typeof(UIManager).Assembly, BusScope.Core, BusAccessLevel.ReadOnly);

// Networking assembly gets full access to Networking scope, but limited access elsewhere
BusManager.RegisterAccess(typeof(NetworkManager).Assembly, BusScope.Networking, BusAccessLevel.ReadWrite);
BusManager.RegisterAccess(typeof(NetworkManager).Assembly, BusScope.Global, BusAccessLevel.ReadOnly);

This helps enforce architectural boundaries and prevents unintended cross-system dependencies.

Request-Response: Two-Way Communication

So far, we've mostly dealt with one-way communication - publishing messages without expecting a direct response. But sometimes you need two-way communication, such as:

  • Requesting player data from a database
  • Checking if an inventory has a specific item
  • Requesting permission to perform an action

SHBI provides a built-in request-response pattern:

// Define a message that requires a response
public class PlayerDataRequest : BaseMessage
{
    public string PlayerId { get; }
    
    // Note the requiresResponse parameter set to true
    public PlayerDataRequest(string playerId) : base(requiresResponse: true)
    {
        PlayerId = playerId;
    }
}

// Handler that responds to the request
void OnEnable()
{
    BusManager.MessageBus.Subscribe(HandlePlayerDataRequest);
}

void HandlePlayerDataRequest(PlayerDataRequest request)
{
    // Get the player data
    var playerData = GetPlayerData(request.PlayerId);
    
    // Send the response
    BusManager.MessageBus.Respond(request, playerData);
}

// Making a request and getting a response
async void LoadPlayerData(string playerId)
{
    try
    {
        // Make the request and await the response
        var playerData = await BusManager.MessageBus.Request(
            new PlayerDataRequest(playerId),
            TimeSpan.FromSeconds(5) // Timeout
        );
        
        // Use the player data
        UpdateUI(playerData);
    }
    catch (TimeoutException)
    {
        Debug.LogError("Request for player data timed out");
    }
}

Timeout Handling

Note the timeout parameter in the request. This prevents your code from hanging indefinitely if no response is received:

// Specify a custom timeout (default is 5 seconds)
var response = await BusManager.MessageBus.Request(
    request,
    TimeSpan.FromSeconds(10) // 10-second timeout
);

Always handle timeouts appropriately, especially for critical operations.

Request Validation

The SHBI system performs several validations to prevent common errors:

// This will throw if requiresResponse isn't set to true
var response = await BusManager.MessageBus.Request(
    new InvalidRequest("data") // Constructor doesn't set requiresResponse = true
);

// This will throw if no handlers are subscribed
var response = await BusManager.MessageBus.Request(
    new ValidRequest("data")
);

Always ensure:

  • Your request message has requiresResponse: true
  • At least one handler is subscribed before making the request

Priority and Order: Who Goes First

Sometimes the order in which subscribers receive messages matters. For example:

  • A logger should record an event before it's processed
  • A validation system should check a request before it's fulfilled
  • Core systems might need to process changes before UI updates

SHBI allows you to specify a priority when subscribing:

// Higher numbers = higher priority (executed first)
// Default priority is 0
messageBus.Subscribe(LogGameStateChange, priority: 100);
messageBus.Subscribe(UpdateGameSystems, priority: 50);
messageBus.Subscribe(UpdateUI, priority: 10);
With this setup, the handlers will execute in this order:
1
LogGameStateChange
priority 100
2
UpdateGameSystems
priority 50
3
UpdateUI
priority 10

Enabling Priority Support

Priority sorting adds a small overhead, so it's configurable:

// Enable priority support when creating a bus
var bus = MessageBusBuilder.Create()
    .WithPrioritySupport()
    .WithScope(myScope)
    .Build();

Use priorities when execution order matters, but be mindful of creating dependencies between your handlers.

Timing Matters: Async Dispatch

Unity is single-threaded for most operations - code generally runs on the main thread. However, sometimes messages might be published from background threads, such as:

  • Network message handlers
  • Asset loading callbacks
  • Background processing threads

SHBI can automatically ensure handlers are called on the main thread:

// Create a bus with async dispatch enabled
var bus = MessageBusBuilder.Create()
    .EnableAsyncDispatch()
    .WithScope(myScope)
    .Build();

// Now publishing from any thread will be safe
// The handler will execute on the main Unity thread

The async dispatcher uses Unity's MonoBehaviour timing system to ensure handlers run at an appropriate time in the frame.

Handling Frame Timing

While async dispatch ensures main thread execution, it doesn't guarantee when in the frame the handler will run. If you need specific frame timing (like after all updates but before rendering), consider:

  1. Using async dispatch to get to the main thread
  2. Then using your own timing mechanism (like LateUpdate or a custom manager) for the actual logic

Lifecycle Management: Staying Memory Safe

A common issue with event systems is memory leaks from forgotten subscriptions. SHBI provides several features to help manage the lifecycle of subscribers:

Manual Subscription Management

The most explicit approach is to subscribe in OnEnable and unsubscribe in OnDisable:

public class PlayerUI : MonoBehaviour
{
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        _messageBus = BusManager.GetMessageBus(BusScope.UI);
    }
    
    private void OnEnable()
    {
        _messageBus.Subscribe(OnPlayerHealthChanged);
    }
    
    private void OnDisable()
    {
        _messageBus.Unsubscribe(OnPlayerHealthChanged);
    }
    
    private void OnPlayerHealthChanged(PlayerHealthChangedMessage message)
    {
        UpdateHealthBar(message.CurrentHealth, message.MaxHealth);
    }
}

Automatic Cleanup for MonoBehaviours

SHBI has built-in protection for MonoBehaviour subscribers:

// Behind the scenes, SHBI tracks if MonoBehaviour subscribers
// have been destroyed and automatically cleans them up

This helps prevent memory leaks, but it's still good practice to manually unsubscribe for predictable behavior.

Checking for Subscribers

Before publishing important messages or making requests, you can check if anyone is listening:

if (messageBus.HasSubscribersFor())
{
    messageBus.Publish(new ImportantMessage("Critical data"));
}

This helps avoid unnecessary message creation and processing when no one is listening.

Real-World Examples: Putting It All Together

Let's explore some complete, real-world examples of using SHBI in a game:

Example 1: Player Health System

// Health message
public class PlayerHealthChangedMessage : ScopedMessage
{
    public float CurrentHealth { get; }
    public float MaxHealth { get; }
    public bool IsDamage { get; }
    
    public PlayerHealthChangedMessage(float currentHealth, float maxHealth, bool isDamage)
        : base(BusScope.Core, PropagationBehavior.UpAndDown)
    {
        CurrentHealth = currentHealth;
        MaxHealth = maxHealth;
        IsDamage = isDamage;
    }
}
// Health component
public class PlayerHealth : MonoBehaviour
{
    [SerializeField] private float maxHealth = 100f;
    private float currentHealth;
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        currentHealth = maxHealth;
        _messageBus = BusManager.GetMessageBus(BusScope.Core);
    }
    
    public void TakeDamage(float amount)
    {
        currentHealth = Mathf.Max(0, currentHealth - amount);
        
        // Publish health changed message
        _messageBus.Publish(new PlayerHealthChangedMessage(
            currentHealth, maxHealth, true));
        
        if (currentHealth <= 0)
        {
            Die();
        }
    }
    
    public void Heal(float amount)
    {
        float oldHealth = currentHealth;
        currentHealth = Mathf.Min(maxHealth, currentHealth + amount);
        
        // Only publish if health actually changed
        if (currentHealth > oldHealth)
        {
            _messageBus.Publish(new PlayerHealthChangedMessage(
                currentHealth, maxHealth, false));
        }
    }
    
    private void Die()
    {
        _messageBus.Publish(new PlayerDiedMessage(gameObject.name, BusScope.Core, PropagationBehavior.UpToParent));
    }
}
// UI health display
public class HealthUI : MonoBehaviour
{
    [SerializeField] private Image healthBar;
    [SerializeField] private ParticleSystem damageEffect;
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        _messageBus = BusManager.GetMessageBus(BusScope.UI);
    }
    
    private void OnEnable()
    {
        // Listen on the UI bus for health messages that propagate up from Core
        _messageBus.Subscribe(OnHealthChanged);
    }
    
    private void OnDisable()
    {
        _messageBus.Unsubscribe(OnHealthChanged);
    }
    
    private void OnHealthChanged(PlayerHealthChangedMessage message)
    {
        // Update health bar
        float healthPercent = message.CurrentHealth / message.MaxHealth;
        healthBar.fillAmount = healthPercent;
        
        // Play damage effect if it was damage
        if (message.IsDamage && damageEffect != null)
        {
            damageEffect.Play();
        }
    }
}
// Game manager
public class GameManager : MonoBehaviour
{
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        _messageBus = BusManager.GetMessageBus(BusScope.Global);
    }
    
    private void OnEnable()
    {
        // Listen for player death at the global level
        _messageBus.Subscribe(OnPlayerDied);
    }
    
    private void OnDisable()
    {
        _messageBus.Unsubscribe(OnPlayerDied);
    }
    
    private void OnPlayerDied(PlayerDiedMessage message)
    {
        Debug.Log($"Player {message.PlayerName} has died! Game over!");
        // Show game over screen, restart level, etc.
    }
}

Example 2: Inventory Request System

// Inventory request message
public class InventoryItemRequest : ScopedMessage
{
    public string ItemId { get; }
    public int Quantity { get; }
    
    public InventoryItemRequest(string itemId, int quantity)
        : base(BusScope.Core, PropagationBehavior.Local, requiresResponse: true)
    {
        ItemId = itemId;
        Quantity = quantity;
    }
}

// Request result
public class InventoryRequestResult
{
    public bool Success { get; set; }
    public string ErrorMessage { get; set; }
    public int QuantityAvailable { get; set; }
}
// Inventory system
public class InventorySystem : MonoBehaviour
{
    private Dictionary _inventory = new Dictionary();
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        _messageBus = BusManager.GetMessageBus(BusScope.Core);
        
        // Initialize with some items
        _inventory["Gold"] = 100;
        _inventory["Potion"] = 5;
        _inventory["Sword"] = 1;
    }
    
    private void OnEnable()
    {
        _messageBus.Subscribe(HandleItemRequest);
    }
    
    private void OnDisable()
    {
        _messageBus.Unsubscribe(HandleItemRequest);
    }
    
    private void HandleItemRequest(InventoryItemRequest request)
    {
        var result = new InventoryRequestResult();
        
        if (_inventory.TryGetValue(request.ItemId, out int quantity))
        {
            result.QuantityAvailable = quantity;
            
            if (quantity >= request.Quantity)
            {
                result.Success = true;
            }
            else
            {
                result.Success = false;
                result.ErrorMessage = "Not enough items";
            }
        }
        else
        {
            result.Success = false;
            result.ErrorMessage = "Item not found";
            result.QuantityAvailable = 0;
        }
        
        _messageBus.Respond(request, result);
    }
    
    public void AddItem(string itemId, int quantity)
    {
        if (_inventory.ContainsKey(itemId))
        {
            _inventory[itemId] += quantity;
        }
        else
        {
            _inventory[itemId] = quantity;
        }
        
        _messageBus.Publish(new InventoryChangedMessage(itemId, quantity, true));
    }
    
    public void RemoveItem(string itemId, int quantity)
    {
        if (_inventory.TryGetValue(itemId, out int currentQuantity))
        {
            _inventory[itemId] = Mathf.Max(0, currentQuantity - quantity);
            _messageBus.Publish(new InventoryChangedMessage(itemId, quantity, false));
        }
    }
}
// Shop system that uses inventory requests
public class ShopSystem : MonoBehaviour
{
    private StandardMessageBus _messageBus;
    
    private void Awake()
    {
        _messageBus = BusManager.GetMessageBus(BusScope.Core);
    }
    
    public async void TryPurchaseItem(string itemId, int cost, int quantity)
    {
        // First check if player has enough gold
        try
        {
            var goldResult = await _messageBus.Request(
                new InventoryItemRequest("Gold", cost),
                TimeSpan.FromSeconds(2)
            );
            
            if (!goldResult.Success)
            {
                ShowError("Not enough gold to purchase!");
                return;
            }
            
            // Remove gold and add item
            _messageBus.Publish(new RemoveItemMessage("Gold", cost));
            _messageBus.Publish(new AddItemMessage(itemId, quantity));
            
            ShowPurchaseComplete();
        }
        catch (TimeoutException)
        {
            ShowError("Request timed out. Try again later.");
        }
    }
    
    private void ShowError(string message)
    {
        Debug.LogError(message);
        // Show UI error message
    }
    
    private void ShowPurchaseComplete()
    {
        Debug.Log("Purchase completed!");
        // Show UI confirmation
    }
}

Debugging Tips: When Things Go Wrong

Even with a well-designed system, issues can arise. Here are some common problems and how to diagnose them:

Problem: Message Not Being Received

Checklist:

  1. Verify you're publishing and subscribing to the same message type (exact same class)
  2. Check you're using the correct bus for the scope
  3. Confirm the subscriber is active when the message is published
  4. Ensure you haven't unsubscribed elsewhere
  5. Verify the execution order (subscriber might be initializing after the message is sent)

Debugging Steps:

// Add logging to publishing
Debug.Log($"Publishing {typeof(MyMessage).Name} to {bus.Scope.Name} bus");
bus.Publish(new MyMessage());

// Add logging to subscription
Debug.Log($"Subscribing to {typeof(MyMessage).Name} on {bus.Scope.Name} bus");
bus.Subscribe(OnMessage);

// Check if there are any subscribers
Debug.Log($"Has subscribers for {typeof(MyMessage).Name}: {bus.HasSubscribersFor()}");

Problem: Message Not Propagating

Checklist:

  1. Verify the message's scope matches the bus's scope (most common issue!)
  2. Confirm the parent-child relationship between buses is properly established
  3. Check that the propagation behavior is set correctly
  4. Ensure parent/child buses exist and are accessible

Debugging Steps:

// Verify bus hierarchy
Debug.Log($"Parent bus: {childBus.ParentBus?.Scope.Name ?? "None"}");

// Check message scope
Debug.Log($"Message scope: {message.Scope.Name}, Bus scope: {bus.Scope.Name}");

// Print full hierarchy path
void PrintScopePath(BusScope scope)
{
    var path = new List();
    var current = scope;
    
    while (current != null)
    {
        path.Add(current.Name);
        current = current.Parent;
    }
    
    path.Reverse();
    Debug.Log($"Scope path: {string.Join(" -> ", path)}");
}

Problem: Request Times Out

Checklist:

  1. Verify at least one handler is subscribed
  2. Ensure the handler is actually calling Respond
  3. Check that the message has requiresResponse: true
  4. Make sure the timeout is appropriate for the operation

Debugging Steps:

// Before making a request
Debug.Log($"Has handler for request: {bus.HasSubscribersFor()}");

// In the handler
void HandleRequest(MyRequest request)
{
    Debug.Log($"Handling request: {request.MessageId}");
    
    // Process...
    
    Debug.Log($"Sending response for: {request.MessageId}");
    bus.Respond(request, response);
}

Problem: Memory Leaks

Checklist:

  1. Ensure all subscribers are unsubscribing when appropriate
  2. Check for static event handlers that might persist
  3. Verify MonoBehaviours are properly implementing OnDisable/OnDestroy

Debugging Steps:

// Add a destructor to detect when objects are garbage collected
~MyClass()
{
    Debug.Log($"MyClass instance being garbage collected");
}

// Count subscribers before and after operations
Debug.Log($"Subscriber count before: {CountSubscribers()}");
// Operation that might cause leak

Performance Optimization: Scaling Up

As your project grows, performance may become a concern. Here are some strategies for optimizing SHBI:

Message Pooling

For high-frequency messages, consider implementing a message pool:

public class VectorMessagePool
{
    private readonly Queue _pool = new Queue();
    private readonly object _lock = new object();
    
    public VectorMessage Get(Vector3 value)
    {
        lock (_lock)
        {
            if (_pool.Count > 0)
            {
                var message = _pool.Dequeue();
                message.Value = value;
                return message;
            }
        }
        
        return new VectorMessage(value);
    }
    
    public void Return(VectorMessage message)
    {
        lock (_lock)
        {
            _pool.Enqueue(message);
        }
    }
}

// Usage
var pool = new VectorMessagePool();
var message = pool.Get(transform.position);
bus.Publish(message);
pool.Return(message);

Batching Messages

For systems that generate many messages, consider batching them:

public class BatchedTransformMessage : BaseMessage
{
    public List<(int EntityId, Vector3 Position, Quaternion Rotation)> Updates { get; }
    
    public BatchedTransformMessage()
    {
        Updates = new List<(int, Vector3, Quaternion)>();
    }
    
    public void AddUpdate(int entityId, Vector3 position, Quaternion rotation)
    {
        Updates.Add((entityId, position, rotation));
    }
}

// Usage
var batch = new BatchedTransformMessage();

foreach (var entity in entities)
{
    if (entity.HasMoved)
    {
        batch.AddUpdate(entity.Id, entity.Position, entity.Rotation);
    }
}

if (batch.Updates.Count > 0)
{
    bus.Publish(batch);
}

Disabling Features You Don't Need

The SHBI system has several features that can be disabled if not needed:

var optimizedBus = MessageBusBuilder.Create()
    // Don't use priority sorting if order doesn't matter
    .WithPrioritySupport(false)
    // Disable async dispatch if all your code runs on the main thread
    .EnableAsyncDispatch(false)
    // Disable advanced logging in production builds
    .WithAdvancedLogging(false)
    .WithScope(myScope)
    .Build();

Limiting Propagation

Be judicious about which messages propagate and how far:

// Instead of UpAndDown propagation for everything,
// be specific about what really needs to travel
bus.Publish(new CriticalMessage("Important", scope, PropagationBehavior.UpAndDown));
bus.Publish(new StandardMessage("Normal", scope, PropagationBehavior.Local));

Filtering Messages Before Creation

Sometimes it's better to check conditions before creating and publishing a message:

// Instead of this:
bus.Publish(new TransformChangedMessage(transform.position));

// Do this:
if (Vector3.Distance(lastPublishedPosition, transform.position) > threshold)
{
    lastPublishedPosition = transform.position;
    bus.Publish(new TransformChangedMessage(transform.position));
}

Best Practices and Common Pitfalls

To wrap up, here are some best practices and common pitfalls to avoid:

Best Practices

1. Organize by Domain

  • Create scopes that match your logical domains
  • Keep related messages within the appropriate scope

2. Design Clear Message Contracts

  • Include all necessary data in the message
  • Use descriptive names that indicate the event or action
  • Consider making messages immutable

3. Handle Lifecycle Properly

  • Subscribe in OnEnable/OnStart
  • Unsubscribe in OnDisable/OnDestroy
  • Be mindful of static subscribers

4. Use the Right Tool for the Job

  • Use events for notifications
  • Use messages for commands or requests
  • Use request-response for operations that need a reply

5. Document Your Message Flow

  • Maintain documentation of your message types
  • Document which systems publish and subscribe to which messages
  • Create diagrams of your scope hierarchy

Common Pitfalls

1. Scope Mismatch for Propagation

  • Always ensure the message's scope matches the bus's scope for propagation to work
  • This is the #1 cause of propagation issues

2. Circular Dependencies

  • Be cautious about systems that respond to each other's messages
  • This can create hard-to-detect circular dependencies

3. Overusing Propagation

  • Don't make every message propagate everywhere
  • Be intentional about message flow

4. Not Checking for Subscribers

  • For critical operations, check if there are subscribers before publishing
  • Handle the case where no one is listening

5. Message Overload

  • Don't create too many message types
  • Group related data in single messages
  • Consider frequency and payload size for performance-critical systems

6. Parent-Child Relationship Errors

  • Ensure buses are properly connected in parent-child relationships
  • This is crucial for propagation to work correctly
